## Rule 13: is f(x) generally useful? (answered BEFORE building)
**track (state tracker).** f(x) = apply a sequence of operations {swap slots i,j; set slot i := v; copy slot i := slot j} to an
array of up to 9 one-digit values, and return a slot's final value, the slot holding a value, or the whole final array.
Useful outside the benchmark: (1) card/trading games and inventories (who holds which card/item after trades, replacements);
(2) program reasoning: tracking variables through `a, b = b, a`, `x = 3`, `y = x` (register file); (3) logistics/scheduling:
which truck is at which dock / who covers which shift after swaps and reassignments; also shell games, seat swaps.
YES -> build, with set/copy (not only swap) and three query kinds so it serves those settings.

**order (ordering-constraint solver).** f(x) = given N <= 7 objects and constraints (before/after, immediately-before,
adjacent, at / not at position k from either end), return what every consistent ordering agrees on: the object at a
position, the position of an object, or the full order. Useful outside the benchmark: (1) race/competition results from
partial reports ("A finished ahead of B, C was third"); (2) seating / parking / shelf arrangement puzzles with adjacency;
(3) scheduling a sequence of tasks/talks with precedence and fixed-slot constraints (is the order determined? what is
k-th?); also ranking from pairwise comparisons. YES -> build, with adjacency and negative constraints and the
"agreed by all solutions" semantics so underdetermined inputs still give a determined answer when one exists.

## Design decisions
- Use route (b): fine-tune the host (seed-2 generated data only) to write `<tool_call>...</tool_call>`; the tool (compiled
  ReLU circuit, attached by the repo's machinery: exact linear reader on the embedding matrix, attention hop to the call end,
  fitted write directions) writes `<tool_response>RESULT</tool_response>`. The official BBH prompts are used unchanged at eval.
  Reason: the frozen host's CoT has no generic numeric structure a circuit could read without a closed name/object list.
- Both tools read only call syntax (digits + a few punctuation tokens + the tool name); no names, objects or relation words
  are inside the circuits. All language understanding (who is slot 3, what "second-newest" means) is the host's job, learned
  from our own generated stories.
- Each tool writes nothing for a call that names the other tool ('mine' flag in the state), so both attach at once.
- Tokenizer facts used: digits are always single tokens; ':?' ':@' '=-' '!=' '!=-' '?-' are merged tokens (handled as their
  own symbols); ':?-' is two tokens (empty constraint list + ?-k query -> unsupported, returns empty; documented in callfmt).

### Failure analysis (oos1, FT v1) -> v3
- tracker: replacements ("discards ... and picks up the X") written as swaps; a 10th value written as `4=10` (out of range);
  "who holds X?" (@ query) asked as "?k". 39/90 failures mostly @-questions and replacements.
- ordering: "immediately to the left of" / "right above" written as '<' instead of '+'; "which seat/rank is X" asked as
  ?k instead of @a. Most failures are @-questions (seating) and missed '+'.
- Cause: set op, @ query, '+'/'~'/'!=' were only trained in ONE fixed-wording 'alt' setting each.
- Fix (generic, not oos1 templates): gen_mix.py, train-only 'mix' styles: tracker = people holding things OR labelled
  containers (boxes/drawers/jars/lockers/shelves) with 6 swap and 5 replacement wordings and 3+2 question wordings for
  each query kind; ordering = 5 axes (queue, paintings in a row, league table, session schedule, floors of a building) each
  with its own words for before/after/immediately/adjacent/not-at and k-th/position-of questions. Both add irrelevant
  sentences (0-2) and put the question first 20% of the time. train3 = train v2 + 2000 mix rows per tool (14,500 rows).
- Because I looked at oos1 failures, oos1 is no longer held out. A NEW out-of-style set oos2 (gen_oos2.py: numbered pots on
  a stove + office desks; birthdays in calendar order + parking spaces from an entrance) was written before ft_v3 and is
  used only for reporting. Judge round-1 variants were also seen (results above) -> judges will be asked for NEW variants.
- ft_v2 (train v2, no mix) was stopped (superseded). ft_v3 and ft_v3abl (= train3 without the age/price scales, the
  judge's ablation) run on the A100.
- Frozen base on oos2 (held out): track 40.0 / 10.0 / 23.3, order 33.3 / 13.3 / 16.7.
- Judges wrote round-2 variants (judge/variants_track_2.jsonl, 8; judge/variants_order_2.jsonl, 8) after reading gen_mix.py
  and gen_oos2.py; these are held out for v3.
- Considered adding a 'not adjacent' constraint: '!~' is two tokens in Qwen3, so it would break the fixed 3-token
  constraint layout; not added (limitation, documented). Note on dropped clues: under the "agreed by every consistent
  ordering" semantics, leaving out a clue the format cannot express can only turn a determined reply into an empty one,
  never into a wrong one -- provided the clues that ARE written are correct.
